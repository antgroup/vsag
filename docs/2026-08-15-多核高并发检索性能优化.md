# VSAG 多核高并发检索性能优化

## 1. 文档目的

本文记录 VSAG 多核高并发检索性能优化任务的问题背景、目标、当前基线和验收方法。
本文是实验和开发工作的内部说明，不把尚未验证的优化结果写成最终结论。

当前状态：基线测试链路已完成，VSAG 业务源码尚未修改，性能优化尚未开始。

## 2. 问题背景

VSAG 是一个使用 C++ 实现的向量检索库。本任务关注 HGraph 等索引在多核 CPU 和高并发查询场景下的检索性能，重点不是改变检索结果，而是在保持召回率和尾延迟约束的前提下提高中高并发 QPS。

项目说明页：<https://summer.ospp.ac.cn/org/prodetail/26c520013?lang=zh>

当前基线在本机的 D 盘 WSL 环境中完成：

- 代码目录：`D:\Project\VSAG`
- 构建目录：`D:\Project\VSAG\build-release`
- 测试机器：AMD Ryzen 5 7640HS，6 个物理核、12 个逻辑线程，约 15.2 GB 内存
- 构建方式：Release，启用 `eval_performance` 工具
- 当前环境的 `perf` 不可用，正式 profiling 需要在原生 Linux 环境完成

本机基线使用合成数据：20,000 条 base 向量、1,000 条 query、32 维、FP32、HGraph、`max_degree=16`、`ef_search=40`。该数据用于验证测试链路和观察趋势，不能替代项目要求的公开数据集和指定硬件。

## 3. 当前基线现象

外层查询并发结果如下。QPS 和 P99 均为同一组固定参数下的测量值：

| 外层并发 | QPS | P99 延迟 |
| ---: | ---: | ---: |
| 1 | 21,075 | 0.080 ms |
| 2 | 40,991 | 0.097 ms |
| 4 | 83,276 | 0.075 ms |
| 8 | 129,295 | 0.103 ms |
| 16 | 134,381 | 0.166 ms |

现象说明：

1. 并发 1 到 4 时接近线性扩展。
2. 并发 8 到 16 时 QPS 仅提升约 4%，出现明显饱和。
3. 并发 16 的 P99 比并发 8 明显升高，说明高并发下存在争用或调度开销。

内部并行搜索参数实验也没有证明“增加线程数”能够解决问题：

| `parallel_search_thread_count` | QPS |
| ---: | ---: |
| 1 | 17,365 |
| 2 | 17,536 |
| 4 | 15,459 |
| 8 | 14,868 |

因此，优化方向应优先解决并发调度、锁和临时对象开销，而不是盲目增加内部线程数。

## 4. 优化目标

### 4.1 性能目标

在项目规定的固定硬件、数据集、索引参数和搜索参数下：

- 在中高并发场景下，优化后 QPS 提升至少 15%。
- 测试外层并发 1、2、4、8、16、32。
- 重点关注 8、16、32 并发下的吞吐量和尾延迟。

### 4.2 正确性和质量目标

- 召回率变化不超过项目规定的 1% 范围。
- P99 延迟相对基线不能恶化超过 10%。
- 不引入数据竞争、死锁、结果不稳定或线程泄漏。
- 保持已有 HGraph 搜索、序列化和 API 行为兼容。

### 4.3 工程交付目标

- 在 3 到 5 个公开或项目指定数据集上完成可复现实验。
- 提供固定参数、构建方式、运行命令和结果输出脚本。
- 提供 profiling 证据，说明优化前后的主要时间消耗变化。
- 提交至少一个可审查的最小化 PR，并补充必要的回归测试。

## 5. 初步优化假设

以下是待 profiling 验证的假设，不是已经确认的最终根因：

1. **读锁开销**：`BasicSearcher` 在访问图邻居时可能获取节点级共享锁；可变索引搜索还会获取全局读锁。
2. **只读索引路径未充分利用**：如果索引构建后不再修改，`SetImmutable()` 可以切换为空锁并跳过部分全局锁。
3. **内外层线程过度订阅**：内部并行搜索会为每个查询向共享线程池提交 worker，外层并发增加后可能争用同一线程池。
4. **忙等和任务提交开销**：内部 worker 通过轮询队列等待任务，每个查询还会重复创建任务和等待 future。
5. **查询临时对象开销**：堆、距离计算器、visited-list 和临时缓冲区的创建与分配可能在高并发下放大。

## 6. 优化实施顺序

### 阶段一：冻结基线

- 在原生 Linux 环境确认 CPU、内存、编译器和 SIMD 能力。
- 使用项目指定数据集和参数，重复运行并记录 QPS、平均延迟、P50/P99、召回率和内存。
- 固定线程数、CPU 亲和性和运行顺序，避免把环境噪声误判为优化收益。

### 阶段二：验证低风险方案

- 确认验收场景是否允许索引构建后进入只读状态。
- 在允许的前提下比较 `SetImmutable()` 前后的锁开销和并发性能。
- 评估查询上下文、visited-list 和临时缓冲区的复用效果。

### 阶段三：优化并发调度

- 根据 profiling 结果限制外层并发与内部并行的组合，避免超过物理核数。
- 对小批量距离计算采用自适应串行路径，避免为少量工作提交 worker。
- 评估固定 worker、批量任务或更合适的同步方式，减少忙等、future 和重复任务创建。

### 阶段四：完整验收

- 每个候选改动先运行单元测试和回归测试。
- 在并发 1/2/4/8/16/32 和全部指定数据集上重复测量。
- 只有同时满足 QPS、召回率和 P99 约束的改动才进入最终 PR。

## 7. 范围边界

本任务聚焦 CPU 侧的多核高并发检索路径，不以使用 GPU 加速为目标。V100 的显卡本身不是 VSAG 当前性能指标的关键；正式结果应以项目规定的 x86_64 CPU、数据集和运行环境为准。

当前合成数据结果仅用于发现瓶颈和验证工具链，不能单独作为“已达到 15% 优化目标”的依据。
