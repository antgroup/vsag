# 邻接维护候选：启发式重选与回填

这是 E14 定位之后的**隔离算法候选**，没有修改 #2904、默认生产库、公共API、格式或CI。
候选结果全部报告；未达到可以宣称项目长期稳定、全面加速或默认修复完成的程度。

## 1. 来源与最小改动

E14 的相同槽位对照已表明显式邻接维护历史影响有限预算召回。
官方 `src/algorithm/hgraph/hgraph_modify.cpp` 的 `graph_force_remove_one` 合并当前邻居与被删节点邻居后，
调用 `src/impl/pruning_strategy.cpp` 的 `select_edges_by_heuristic` 重选。
Lite 原 `repair` 主要保留已有边并补缺额，本候选仅替换这个函数：

- 合并当前有效边与原有 additional_candidates，去重、排除越界与自身，按原距离排序。
- 使用 alpha=1 的 occlusion 规则优先保留方向分散的边，再从剩余近邻回填到原有 degree 上限。
- 对失去出边引用的旧目标继续执行原 ensure_incoming；仍使用原 mutation journal。

“回填”是 Lite 特有的边数保持约束，不是照搬 HGraph；不会引入 Full 依赖或新公开开关。
没有新增候选搜索预算，degree 上限16、建图ef128、查询ef512固定；实际路由工作量不因此保证相同。
只有独立目录的一个TU overlay，所有其他对象、编译选项、输入和公共查询实现保持原样。

## 2. 失败候选也保留

第一版只做启发式筛边，没有回填，被已有回归测试拒绝：
`Lite graph repeated CRUD repairs affected adjacency` 的边数断言为1580，而要求至少3072。
该版 Release CTest 为4/5，未进入GIST实验，明确否定。
第二版加回填后 Release5/5、ASan/UBSan5/5、format/tidy15通过。
没有删测试、降低断言或把第一版报为优化成功。
扩展controller首次因漏定义证据路径而在首组后处理停止；补全路径后校验并复用已完成的原始结果，
没有重跑挑最好的一次。首次controller和失败日志同样保留。

## 3. 全部末轮质量

先做 GIST/FP32 原值重插试验：基线0.9125、候选0.9811；初始快照SHA完全相同、末轮ef=N均1.0000。
随后预先固定下列7个扩展单元，每单元每版本一个新进程，交替先后顺序。
每组100轮×250cycles；只有Update或只有Remove/Add，不含交错查询、轮间Save/Load或中途质量点。
因此这是维护后的质量候选诊断，不能冒充 E14 resident 正式性能矩阵。

| 数据 / 存储 / 操作 | 基线 ef512 | 候选 ef512 | 差值（百分点） | 基线 ef=N | 候选 ef=N |
|---|---:|---:|---:|---:|---:|
| GIST / fp32 / update | 0.9280 | 0.9369 | +0.89 | 1.0000 | 1.0000 |
| GIST / fp32 / replace | 0.9106 | 0.9662 | +5.56 | 1.0000 | 1.0000 |
| GIST / fp16 / update | 0.9272 | 0.9350 | +0.78 | 0.9991 | 0.9991 |
| GIST / fp16 / replace | 0.9091 | 0.9663 | +5.72 | 0.9991 | 0.9991 |
| GIST / fp16 / reinsert | 0.9137 | 0.9829 | +6.92 | 0.9998 | 0.9998 |
| SIFT / fp32 / reinsert | 0.9934 | 0.9988 | +0.54 | 1.0000 | 1.0000 |
| Cohere / fp32 / reinsert | 0.9716 | 0.9873 | +1.57 | 1.0000 | 1.0000 |

所有组逐字节核对初始快照、最终ID槽位和存储向量；GIST基线末轮快照SHA还复现E14正式实验。
同数据常规/同槽位重建结果在两个库下有序ID和距离完全一致，正式ef512与全预算结果分开保留。
每个实际输入10000向量、1000查询行，真值是针对当前实际子集和当前向量计算的FP64 Top10。
同一查询集、单个图实例的改善不等于多种随机建图、100k或小时级耐久保证。
RaBitQ 后端另有图维护实现，本轮没有把 FP32/FP16 候选冒充 RaBitQ 修复。

## 4. 成本不能省略

## 5. 复现和证据

`raw.tar.gz` / `archive.json` 含第一版失败、第二版完整overlay、原始逐查询CSV、源码、计划、编译/链接命令、
实际库绑定检查、SAN日志和快照收据。已有E10–E14不变，没有上传候选为默认生产文件。
大型临时快照在完成全部向量/槽位核对并保存SHA后回收；原始CSV和重放程序不删除。
原输入不随包分发；输入路径/哈希、源码身份与所有命令保留，不能以新SHA重标旧库。

重跑请在两个独立功能检出构建基线/候选；只给候选检出应用归档 `r2/candidate.diff`，不要应用到2904。
两边都使用相同CMake选项，先通过既有Release/SAN测试。随后编译归档 `followup/probe.cpp`，
分别绑定两个实际库运行相同输入/参数（`OUTPUT`必须不存在）：

```bash
LD_LIBRARY_PATH="$CONTROL_BUILD" taskset -c 0 "$PROBE" "$DATASET" "$CONTROL_OUTPUT" update 100 250 fp32
LD_LIBRARY_PATH="$CANDIDATE_BUILD" taskset -c 0 "$PROBE" "$DATASET" "$CANDIDATE_OUTPUT" update 100 250 fp32
# 其他单元严格按 plan.json；模式 replace/reinsert，存储 fp32/fp16，不挑最好的一次。
```

验证初始快照一致、最终向量/槽位一致、真值/重建结果一致，并对每条查询重算Recall。
先解包后阅读 `audit.json`、`followup/rows.json`、计划和全部源码；归档controller记录实际服务器路径，
换机器时应使用自己的独立路径及同版本依赖，不能去掉来源校验冒充完全相同的二进制。
下一步是重复配对的真实混合CRUD、查询尾延迟和内存成本验证，以及RaBitQ独立诊断；未宣称全部验收完成。
