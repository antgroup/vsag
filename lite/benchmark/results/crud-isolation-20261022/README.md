# GIST CRUD 隔离：Update 与 Remove/Add

本轮只增加 benchmark 诊断和证据，不改 #2904、不改生产算法。
正式结果全部使用 query ef=512；末轮 ef=N 单列为诊断，不当作优化成绩。
原始审计通过不等于长期质量已经达标；召回只报告实测值，不设项目硬门槛。

## 1. 三组实验分别改变什么

| 工作负载 | 每个 cycle | 向量数据 | 每存储修改 API 调用数 |
| --- | --- | --- | --- |
| 仅 Update 改值 | Update → Query | FP32 变值配方 | 25000 |
| Remove/Add 改值 | Remove → Query → Add → Query | API输入/真值的逻辑向量与 Update 组相同 | 50000 |
| Remove/Add 原值 | Remove → Query → Add → Query | 整个实验中逻辑数据始终不变 | 50000 |

同一 ID 序列，100 轮×250 cycles，GIST 10000×960，1000 查询行（998 种不同内容），
CPU0、单线程、degree16/build ef128/query ef512/k10，每组每存储一个新进程，共9进程。
合计375000次修改API、375000次交错查询、900次Save及900次Load。
同样预触达完整测量缓冲区；原 resident 对象从不被 Load 或重建对象替换。
本轮临时快照写入 `/dev/shm` RAM 文件系统，用于格式和显式保存/加载一致性核对，
不是磁盘I/O、逐操作落盘或断电持久性测量；实际部署加载/包体对照仍以 E11 为准。

每25轮，在隔离子进程中计算当前 FP64 真值并用相同当前向量、相同 ID 重建。
共45个检查点，保留全部45000个查询状态的真值与90000次固定预算查询结果。
Update/改值重插的变值配方都是 `.875F * current[id] + .125F * original[donor]`，每cycle只应用一次。
RaBitQ 重建还会重新训练模型，不能把它的全部差值都解释为图结构。

## 4. 能定位到哪一层，不能定位到哪一行

- **原值重插控制**：逻辑数据始终不变，但FP32/FP16/RaBitQ的召回分别从0.9646/0.9645/0.9607降至0.9125/0.9137/0.9346，下降5.21/5.08/2.61个百分点；本组退化不能归因于当前向量分布改变。
- **相同数据控制**：Update 与改值重插的真值及重建结果一致，它们维护结果的差异来自各自的维护历史（包括连边和内部槽位/入口顺序），不是当前数据难度不同。
- **路由诊断**：本轮三组FP32在末轮ef=N全部恢复到1.0000；FP16也达到相同当前数据重建的全预算值。正式ef512的损失主要发生在有限预算图搜索，不能仅用持久化文件是否及时保存解释。
- **量化边界**：RaBitQ改值两组ef=N为维护0.9958、重建0.9951，而原值组两者均0.9955；保留固定模型与重训、编码/排序的影响，不能把RaBitQ全部差值归为图修复。Update与改值重插在ef=N下全部有序ID及距离相同。
- **持久化控制**：每轮1000条查询的保存前后有序ID及距离相同，原内存对象不被加载副本替换。本轮不支持“这条内存召回曲线由读取旧快照造成”；但不证明逐操作落盘、WAL、断电恢复或并发一致性。

源码中 FP32/FP16 的 Update 会重选更新节点的邻居，并对受影响入边做局部修复；Remove 会移尾槽、重映射邻接并局部补边。
`repair` 主要保留已有有效边、按距离填补缺额；查询还依赖槽位相关的隐式环边和多入口。
因此，这些实验隔离的是动态维护/槽位历史及有限预算路由质量，**尚不能单独判定某一条 repair 代码是唯一根因**。
同槽位顺序控制见下节；后续仍应检查邻居候选和路由访问，再设计最小修复。
不能盲加 ef、照搬 HGraph 或把重建直接宣传为无成本修复。

### 4.1 额外控制：固定相同内部槽位顺序再重建

这两组 FP32 诊断在全部计时实验结束后单独执行，不用于速度比较。
只重放公共API，去掉计时、交错查询与中途Save/Load；要求最终快照大小/SHA与正式矩阵完全一致，
并要求逐查询的维护/常规重建有序结果复现正式末轮。
独立模拟每次删除的移尾槽和重插顺序，再读取实际快照ID序列逐项核对；
三种视图的全部10000×960个FP32存储值，还与独立NumPy变值重放逐字节核对。

常规重建按ID顺序，相同槽位重建按维护索引的最终槽位顺序：
后者固定了查询的槽位入口与隐式环边对应关系，但重新生成显式邻接，进一步控制布局因素。

| FP32 工作负载 | 维护 ef512 | ID顺序重建 | 同槽位重建 | 三者 ef=N |
| --- | --- | --- | --- | --- |
| Remove/Add 改值 | 0.9106 | 0.9447 | 0.9413 | 1.0000 / 1.0000 / 1.0000 |
| Remove/Add 原值 | 0.9125 | 0.9646 | 0.9631 | 1.0000 / 1.0000 / 1.0000 |

本次两组中，固定相同槽位顺序后重新生成邻接，召回仍高于维护索引。槽位重排本身不能单独解释维护损失；相同向量、入口/环边对应关系和预算下，显式邻接的维护历史是已被对照锁定的质量因素。不能由此进一步武断地指认某一行代码为唯一原因。

源码和全部逐查询结果保留于原始归档的 `slot-controls/`。该控制只覆盖FP32、两个末轮状态；
不升级为FP16/RaBitQ结构证明，也不是新的算法修复或长期性能成绩。
需要重跑时，先解开三个测量cohort，使用归档中的可移植控制脚本和相同测量库：

## 7. 复现、独立检查与限制

使用本分支工具和干净的功能检出；按主复现指南生成 source-bound build receipt。
测量库与 E13 相同；实际工具源码、编译命令、加载库、输入哈希和全部命令保留在原始包内。
新生成的功能源码提交身份与旧测量身份分开记录，不能删掉 guard 给旧库贴新版本。

```bash
# BENCH_ROOT / BENCH_WORK / BENCH_FEATURE / BENCH_FEATURE_SHA / BENCH_FEATURE_BUILD
# 按 canonical 复现指南建立；GIST_DATA 必须为匹配哈希的10k/1000查询准备目录。
for workload in update replace reinsert; do
  python3 "$BENCH_ROOT/lite/benchmark/run_mixed_cpu_acceptance.py" \
    --feature-repo "$BENCH_FEATURE" --feature-sha "$BENCH_FEATURE_SHA" \
    --build "$BENCH_FEATURE_BUILD" --dataset "GIST=$GIST_DATA" \
    --trials 1 --rounds 100 --cycles 250 --cpu 0 --resident \
    --checkpoint-every 25 --mutation-mode "$workload" \
    --output "$BENCH_WORK/isolation-$workload"
  python3 "$BENCH_ROOT/lite/benchmark/verify_mixed_cpu_acceptance.py" "$BENCH_WORK/isolation-$workload"
  python3 "$BENCH_ROOT/lite/benchmark/pack_mixed_cpu_acceptance.py" "$BENCH_WORK/isolation-$workload"
done
```

旧默认 `all` 参数/计数/输出保持兼容。三存储小fixture与父版本逐质量CSV、邻居CSV和每轮快照哈希完全一致。
独立 NumPy FP64 重放：预先固定10条查询×5检查点×2种数据轨迹，共100个查询状态，每次遍历全部10000向量；不是对45000条真值做第二遍全量距离校验。
全量45000查询状态另外检查存储间真值、改值两组真值、重建有序结果以及原值重插不变性。
5000次、seed20261022 的查询内容聚类bootstrap保留在 `analysis/paired.json`，998组重复查询聚类；只反映固定图条件下查询不确定性，不是多次建图置信区间或项目验收门槛。

本轮一个进程/单元、一个GIST规模，完整报告但不宣称跨分布、100k、小时耐久或Full动态性能已验证。
没有新的算法优化结果，没有修改生产API、存储格式、CI配置或 #2904。
补充同槽位程序第一次在计时前因多变量同声明被clang-tidy15拒绝；拆开声明后重新编译、tidy和两组重放通过。
失败日志与首次源码也保留在 `preflight-failure/`，不是删除失败后只展示成功运行。
